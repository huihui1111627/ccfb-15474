# 带内遥测采集 / 处理 / 分析系统

In-band Network Telemetry (INT) testbed for a data-centre fabric, written in
Python + NumPy.  Everything the collector sees comes from a simulated wire;
there is no ground truth in the collector's inputs.

The problem it addresses is the one where the application team says "the
network is slow" and the network team says "the counters are flat".  Minute-
level interface counters cannot see a 30 ms queue that builds and drains
twice a second.  Per-packet in-band telemetry can — but only if you can
afford to carry it, and only if you can put it back together afterwards.

| 需求 | 实现 |
|---|---|
| 仿真真实数据中心 | 3 层 fat-tree，22 台交换机、64 台主机、128 条路径；交换机间时钟有偏置和漂移；间歇性拥塞、端口限速、链路误码重传 |
| 1. 打标 / 逐跳追加 / 截断 / 终点剥离 | 源端按策略打标，每跳追加 12 B 记录；元数据上限 72 B，7 跳路径必须截断，采用 `key_hops` 策略保留最拥塞跳和最后一跳 |
| 2. 采样策略 | 固定比例 / 分层（按业务、按路径）/ 自适应（分层 + 交换机触发器全量标记） |
| 3. 逐跳还原 + 时钟校正 + 聚合 | 拓扑 + ECMP 哈希精确还原被截断的跳；低分位数拟合消除交换机时钟偏差；按五元组聚合 |
| 4. 慢请求归因 | 给定时间 + 五元组 → 路径、每跳排队时延分解、主要拥塞跳、同端口并发流 |
| 5. 数据量预算 | 把触发器开销和基数概率都计入成本，按“每字节捕获慢请求数”做水位填充 |
| 页面 | 逐跳时延分解、拓扑队列热力图、采样比例变化 |

## 快速开始

```bash
python3 -m itel serve                      # 控制台 http://127.0.0.1:8765
python3 -m itel evaluate --budget 1 2 4    # 验收报告（JSON）
python3 -m itel evaluate --seeds 7 11 23   # 多随机种子
python3 -m pytest tests -q                 # 25 个测试
```

服务启动时会构建一次仿真（约 8 秒，85 万个包）。页面顶部可以改随机种子和
预算并重建。

## 验收结果

`python3 -m itel evaluate --budget 0.6 1.0 2.0 4.0 --with-control`

参照场景：2 秒、847 134 个包、10 134 条流、4 329 笔事务，其中 68 笔端到端
≥ 5 ms，31 笔是网络原因。注入的故障：一条链路被限速到 40%、一个端口间歇性
降速、两条链路各有一段误码重传窗口、两台交换机时钟偏差 ±60–80 ppb。

| 收集器预算 | 自适应捕获率 | 固定采样捕获率 | 自适应归因 | 固定归因 | 自适应 MAE | 固定 MAE |
|---|---|---|---|---|---|---|
| 0.6 MB/s | **51%** | 15% | 100% | 100% | 2.8 µs | 3.9 µs |
| 1.0 MB/s | **68%** | 24% | 100% | 100% | 2.8 µs | 2.6 µs |
| 2.0 MB/s | **88%** | 40% | 100% | 93% | 3.3 µs | 2.9 µs |
| 4.0 MB/s | **100%** | 59% | 100% | 95% | 3.8 µs | 3.6 µs |

归因列是“网络原因慢请求”（端到端 ≥ 5 ms 且服务器处理时间不占主导）中，
定位到的拥塞跳与仿真真值一致的比例。逐跳时延 MAE 是收集器估计的排队时延
与仿真真实排队时延的平均绝对误差。完整 JSON 见 `results/acceptance.json`
（`python3 -m itel evaluate --budget 0.6 1.0 2.0 4.0 --with-control` 可复现）。

“捕获率”= 慢请求中至少有一个响应包携带遥测的比例（这是能做归因的最低要求）。
两组数据量按实际字节对齐（误差 < 2%）。

无故障对照组（同样的拓扑和流量，不注入任何故障）：逐跳时延 MAE 5.6 µs，
此时真实的 P99 排队只有 513 µs —— 也就是说估计误差量级远小于要检测的
现象。

> 说明：自适应采样在低预算下的捕获率受限于触发器自身的字节开销
> （534 kB/s）。触发器阈值是可调的（`TelemetryConfig.queue_trigger_us`
> 与 `trigger_window_us`），这是一个明确的工程折中：窗口越短，数据量越小，
> 但可能漏掉队列排空之后才到达的报文。

## 设计要点

### 仿真

`itel/topology.py` 建一个 k=4 的 3 层 fat-tree：8 台 leaf、8 台 agg、
4 台 spine、2 台 super-spine，每台 leaf 挂 8 台主机。每个有向链路在源交换机
上有一个独占的 FIFO 出口队列，所以同一条链路的两个方向互不影响。

`itel/traffic.py` 生成请求/响应事务和批量传输。业务分类：`web`、`rpc`、
`cache`（命中热存储节点）、`storage`、`backup`。突发性来自把随机间隔的包
压到网卡线速，产生微突发。

`itel/sim.py` 的数据平面是解析的，不是逐包事件循环：对每个出口端口，按
服务开始时间排序后，一包的排队时延等于“前一个包完成时间 − 本包开始服务
时间”，端口内是 `np.maximum.accumulate`，所以 85 万个包 × 7 跳约 0.2 秒。
出口缓冲容量是有界的，超出部分按尾丢弃建模——这一点很关键，否则字节计数器
（上限就是缓冲大小）无法解释超过缓冲排空时间的时延。

### 标记与截断

一条记录 12 字节：

```
sw_id(1) in_port(1) out_port(1) flags(1) qdepth(2, ×128B) ts(6, 48-bit ns)
```

基础头 24 字节（五元组、序号、源端时间戳）。默认上限 72 字节，所以 7 跳
路径只能保留 5 条记录。`key_hops` 策略保留队列最深的几条记录加最后一跳
（最后一跳证明报文确实到达，能闭合路径）。被截断的包会置 `TRUNC` 位。

`first_k` / `last_k` 也在实现里，对比很容易——但注意 `last_k` 会丢掉最拥塞
的那一跳，而这正是要查的东西。

### 采样

- **固定比例**：每包独立伯努利采样，无触发器。用来做基线。
- **分层**：概率 = 基数 × 业务倍数 × 路径倍数。
- **自适应**：在分层之上，交换机本地监测出口队列；积压超过阈值
  （默认 3 ms 的排空时间）或驻留超过阈值，就在接下来 100 µs 内对**所有**
  经过它的包全量标记。触发器是因果的，只看本地队列，不需要任何全局信息。

预算优化器（`itel/sampling.py: optimize_budget`）把所有成本计入：
每条记录 12 B、基础头 24 B、收集器索引 8 B，并按 (业务, 路径) 分层统计
包速率和慢事务速率。基数概率作用于**所有**流量（包括不进层的批量流），
所以这一项按全量包速率计价；各分层的额外概率按各自速率计价。然后按
“每字节期望捕获慢请求数”做贪心水位填充。

### 收集器

`itel/collector.py` 只接收线上的字节。

1. **路径还原**：收集器知道拓扑和 ECMP 哈希种子，所以一个 5 元组对应唯一
   一条路径。被截断的跳是“观测缺失”，不是“路径未知”；每跳的交换机、端口
   都能补全，只有时间戳缺失。
2. **时钟校正**：`ts_sw(t) = t + offset_sw`。对相邻两个观测跳 a→b，
   真实间隔由拓扑已知（传播 + 串行化 + 交换）到排队误差以内，所以
   `ts_b − ts_a − gap = offset_b − offset_a + 排队`。排队只增不减，因此取
   每一对交换机的低分位数就是时钟差，再全局最小二乘解出所有 offset。
   绝对 offset 不可辨识（没有同步参考），但每跳时延只用到**差值**，
   所以这不影响结果。
3. **逐跳分解**：驻留 − 传播 − 串行化 − 交换 = 排队。跨截断跳的时间差
   不能分解（混进了中间跳的排队），此时回退到字节计数器；收集器还会从
   遥测数据本身学习每个端口的**实际**排空速率（限速端口的速率远低于标称
   线速），并按时间分桶跟踪，这样端口降速期间字节换算依然正确。
4. **聚合与归因**：按五元组聚合事务；归因时用响应报文序列中每跳的
   **平均**排队时延（而不是“最惨的那一个包”），因为一次突发会让第一个包
   承担全部队列、后面的包少等——运维关心的是“这笔请求的时延里有多少排在
   第 k 跳”。同端口并发流的窗口按观察到的时延缩放。

## 页面

`http://127.0.0.1:8765/`

- 顶部 KPI：网络原因慢请求数、P99、捕获率、归因准确率、逐跳误差、数据量
- 队列深度热力图：拓扑图按队列时延着色，时间轴可拖动
- 全网最大队列深度时间序列
- 慢请求列表，点击展开逐跳分解；`?txn=997` 可直达
- 采样比例曲线（自适应 vs 固定 vs 触发器全量），触发器次数
- 响应包时间线：每个包何时发出、何时到达，颜色按时延
- 验收对比卡片

## 已知限制

- 数据平面是解析的，不模拟 ACK、重传定时器、拥塞控制；重传体现在单向
  时延上（串行化 + 快速重传惩罚），不改变流量模型。
- 时钟模型是偏移 + 线性漂移。跑 2 秒时漂移只有几十纳秒，低于每跳读数
  抖动，所以收集器只拟合偏移；真实部署里需要长时间窗口才能分出来。
- 预算优化器的分层粒度是 (业务, 路径)，路径数随 pod 数平方增长；更大规模
  需要按 pod 对聚合，而不是逐路径。
- 触发器阈值是固定的；真实部署会用历史分位数自适应。
